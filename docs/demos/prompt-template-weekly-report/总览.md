# Prompt Template 周报生成 Demo 总览

## 1. Demo 目标

`prompt-template-weekly-report` 是 AI-Journey-Land 的第一个端到端 demo，用来验证一件事：如何把 AI-Journey-Fighting 中的 Prompt Template 学习脚本，整理成 Land 中可交互、可展示、可复盘的工程模块。

本次 demo 完成了从“脚本运行”到“平台展示”的第一轮工程化：

- 用页面表单替代脚本中的固定输入。
- 用 NestJS API 保护模型密钥并统一请求入口。
- 用共享 schema 固定输入结构。
- 用 demo registry 记录元信息、页面路由、API namespace 和来源上下文。
- 同时支持普通运行和 SSE 流式运行。
- 在页面侧展示源码对照、关键业务逻辑和学习目标。

## 2. 开发情况

当前 demo 已经跑通完整链路：

1. 首页橱窗从 `demo-registry` 读取 demo 信息。
2. 用户进入 `/demos/prompt-template-weekly-report` 独立页面。
3. 前端表单收集周报输入字段。
4. 普通运行调用 `POST /api/demos/:id/run`，等待完整文本返回。
5. 流式运行调用 `POST /api/demos/:id/stream`，通过 SSE 持续接收 token。
6. 后端根据 `AI_PROVIDER` 选择 OpenAI-compatible 或 DeepSeek 配置。
7. 模型输出展示在固定高度的结果窗口中，避免长文本撑破页面。

## 3. 主要实现思路

本次实现没有把 demo 做成独立微服务，而是采用“微服务思维、模块化单体落地”：

- Web 仍在 `apps/web` 中统一承载，但 demo 页面按路由和组件边界拆分。
- API 仍在 `apps/api` 中统一部署，但 demo 逻辑放进独立 Nest service。
- 元信息由 `packages/demo-registry` 管理，避免前端、后端、文档各写一份 demo 配置。
- 输入类型和请求结构由 `packages/shared` 维护，降低前后端字段漂移风险。
- 模型创建放在 `packages/ai-core`，为后续 provider adapter、stream helper、embedding factory 预留位置。

这个思路的重点是先把边界练清楚：输入、输出、页面、API、AI 调用、来源链接和复盘文档都要有稳定位置。

## 4. 难点与要点

比较关键的难点有几个：

- **真实模型配置**：不能把 key 暴露给前端，所以所有 provider 配置都在后端读取，并通过 `AI_PROVIDER` 明确选择。
- **普通输出与流式输出并存**：普通运行更适合等待完整 Markdown，流式运行更适合学习 token 输出过程，两者的交互反馈不能混在一起。
- **长文本展示**：模型生成的周报可能很长，需要限制输出区域高度，并在 streaming 时每 3 秒自动滚到底部，兼顾“看到新内容”和“不频繁打断阅读”。
- **来源可追溯**：页面不仅展示重构后的 demo，还要保留 Fighting 原始源码，帮助对照学习路径。
- **文档沉淀**：demo 完成后必须有复盘文档，记录为什么这样设计、当前还缺什么、后续如何优化。

## 5. 当前结论

这个 demo 验证了 Land 的第一版基本范式：

- Fighting 负责学习现场和原始实验。
- Land 负责二次验证、接口化、页面化和复盘。
- demo 不只是一个能跑的接口，还要能解释、能展示、能追溯、能继续演进。

后续接入新的 Structured Output、Runnable、Tool Calling、RAG demo 时，可以复用这套路径：先注册元信息，再明确输入输出，再实现 API 和页面，最后补齐 demo 文档包。

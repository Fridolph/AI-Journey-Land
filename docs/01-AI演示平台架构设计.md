# AI 演示平台架构设计

## 1. 设计目标

AI-Journey-Land 的目标是搭建一个个人 AI Demo 展示与工程化验证平台。

它要解决的问题不是“再写几个 demo”，而是把已经学过、跑通过的 demo 变成：

- 可通过接口调用
- 可在页面交互
- 可复用模型初始化逻辑
- 可观察流式输出过程
- 可追溯源码和学习文档
- 可逐步扩展到 RAG、Agent、Evaluation 等复杂场景

## 2. 总体架构

建议采用全栈 monorepo：

```text
AI-Journey-Land
├── apps/
│   ├── api/
│   └── web/
├── packages/
│   ├── ai-core/
│   ├── demo-registry/
│   └── shared/
└── docs/
```

### apps/api

NestJS 后端服务。

负责：

- 管理模型 provider
- 封装 demo service
- 暴露 REST API
- 暴露 SSE streaming API
- 保护 API Key
- 统一错误处理
- 后续接入数据库、向量库、任务队列等能力

当前采用模块化单体结构：API 仍是一个 NestJS 应用，但每个 demo 进入平台时都应该拥有自己的 feature module/service。公共 catalog API 由 `DemosModule` 统一暴露，具体运行逻辑委托给对应 demo module。

### apps/web

Nuxt 4 + Vue 3 + Nuxt UI 前端展示平台。

负责：

- 展示 demo 橱窗首页
- 展示 demo 独立详情页
- 提供输入表单
- 展示普通输出
- 展示流式输出
- 展示运行日志
- 链接源码、文档和学习草稿

首页只负责 catalog/showcase；点击 demo card 进入 `/demos/:id`。简单 demo 可以复用通用 runner 组件，复杂 demo 可以拥有自己的页面结构和交互方式。

### packages/ai-core

统一 AI 调用核心。

建议包含：

- model factory
- embedding factory
- provider adapter
- streaming helper
- structured output helper
- common error
- token usage 统计

目标是避免每个 demo 重复写模型初始化。

第一版已经落地 `createChatModel()`，统一读取后端环境变量中的 `OPENAI_API_KEY`、`OPENAI_BASE_URL` 与 `MODEL_NAME`，并通过 `@langchain/openai` 调用 OpenAI-compatible provider。

### packages/demo-registry

Demo 注册中心。

建议每个 demo 都注册元信息：

```ts
interface DemoMeta {
  id: string
  title: string
  description: string
  category: string
  tags: string[]
  coverImageUrl?: string
  coverAlt?: string
  routePath: string
  apiNamespace: string
  displayMode: 'custom-page' | 'generic-runner'
  ownerPackage: string
  supportsStreaming: boolean
  sourceUrl?: string
  docsUrl?: string
  draftUrl?: string
}
```

这个 registry 同时服务后端和前端：

- 后端知道有哪些 demo 可以运行
- 前端知道如何展示 demo 与跳转到哪个路由
- 文档知道 demo 的来源、能力和边界

### packages/shared

共享类型与 schema。

建议包含：

- DTO
- API response 类型
- demo input/output 类型
- schema 定义
- 通用工具函数

## 3. API 草案

### 获取 demo 列表

```http
GET /api/demos
```

返回：

```json
{
  "items": [
    {
      "id": "prompt-template-weekly-report",
      "title": "Prompt Template 周报生成",
      "category": "Prompt Engineering",
      "supportsStreaming": true
    }
  ]
}
```

### 获取 demo 详情

```http
GET /api/demos/:id
```

返回 demo 元信息、输入 schema、说明文档链接等。

### 普通运行 demo

```http
POST /api/demos/:id/run
```

请求：

```json
{
  "input": {
    "companyName": "极光云科技",
    "teamName": "订单结算后端组",
    "managerName": "陈总",
    "weekRange": "2026-05-04 ~ 2026-05-08",
    "teamGoal": "本周以稳定性为主，集中清理历史技术债和高频告警。",
    "devActivities": "- 老王：修复高优先级线上 Bug 7 个"
  }
}
```

返回：

```json
{
  "demoId": "prompt-template-weekly-report",
  "status": "success",
  "output": "..."
}
```

### 流式运行 demo

```http
POST /api/demos/:id/stream
```

返回 SSE 事件：

```text
event: token
data: {"text":"你好"}

event: done
data: {"status":"success"}
```

当前约定的 SSE 事件为 `meta`、`token`、`done`、`error`。

## 4. 第一批 demo 设计

### Prompt Template Demo

目标：

- 展示 prompt 变量填充
- 展示 system / human message 组合
- 展示 Few-shot 示例选择

适合第一批接入，因为依赖少、输入输出清晰。

### Structured Output Demo

目标：

- 展示模型如何输出 JSON
- 展示 schema 约束
- 展示 parser 失败和修复
- 展示业务系统为什么需要稳定结构化输出

这个 demo 非常适合作为“AI 进入工程系统”的代表。

### Runnable Demo

目标：

- 展示 chain
- 展示 branch
- 展示 retry
- 展示 fallback
- 展示组合式 AI workflow

后续可以做成可视化流程图。

## 5. 前端页面草案

第一版页面采用 Nuxt 4 + Vue 3 + Nuxt UI 实现，入口采用橱窗式 catalog：

```text
/
├── Demo Hub Header
├── Demo Cards
└── Category / Tags / Capabilities

/demos/prompt-template-weekly-report
├── Demo Header
├── Input Form
├── Output / Streaming Panel
└── Source / Docs / Known Limits
```

核心不是视觉复杂，而是交互清楚：

- 我正在浏览哪些 demo
- 我打开的是哪个独立 demo 页面
- 这个 demo 学什么
- 我输入了什么
- 模型返回了什么
- 过程中发生了什么
- 相关源码和文档在哪里

这个结构也为未来更复杂的 demo 留出空间：RAG demo 可以做检索结果区，Agent demo 可以做步骤轨迹，语音 demo 可以做录音与转写面板，不需要被单一通用 runner 限制。

## 6. 部署策略

GitHub Pages 只能托管静态站点，不适合直接跑 NestJS 后端。

建议：

- 文档或静态前端：GitHub Pages / Vercel
- NestJS API：Render / Railway / Fly.io / VPS / Vercel Serverless
- API Key：只放后端环境变量

第一阶段可以先本地运行：

```bash
pnpm dev
```

当前本地端口约定：

- Nuxt Web：`http://localhost:4040`
- Nest API：`http://localhost:4041/api`

后续再考虑线上部署。

## 7. 与 Fighting 的链接策略

Land 中每个 demo 都应该保留来源信息：

- `sourceUrl`：Fighting 中的原始源码
- `docsUrl`：Fighting 文档站中的正式说明
- `draftUrl`：Fighting 中的学习草稿

链接优先级建议：

1. 有正式文档，优先链接正式文档
2. 没有正式文档，链接源码或草稿
3. 页面上可以同时展示源码、文档和草稿

## 8. 风险与取舍

### 不要一开始就做太大

这个项目容易膨胀。

第一阶段只做一个最小闭环：

- 一个后端
- 一个前端
- 一个 demo
- 一个普通接口
- 一个 streaming 接口

先跑通，再扩展。

### 不要把 examples 直接搬过来

Fighting 中的 examples 是学习现场，不一定适合直接成为平台代码。

Land 应该做的是：

- 参考 examples
- 抽取稳定逻辑
- 重新封装成 service
- 通过 registry 暴露给平台

### 不要让前端接触密钥

所有模型调用必须走后端。

前端只负责交互和展示。

## 9. 第一阶段验收标准

完成第一阶段时，应该能做到：

- 打开前端页面
- 看到 demo 列表
- 选择一个 demo
- 填写输入
- 点击运行
- 后端调用模型
- 前端展示结果
- 至少一个 demo 能流式输出
- 页面能跳转到 Fighting 中对应源码或文档

这个闭环跑通后，再接入更多 demo 就会自然很多。

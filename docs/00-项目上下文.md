# 项目上下文

## 背景

当前 AI 学习已经在 `AI-Journey-Fighting` 中积累了不少内容：

- AI 基础概念
- Prompt Template
- Structured Output
- Runnable
- Tool Calling
- RAG
- Memory
- LangGraph
- 多个本地 demo 与学习草稿

这些内容适合作为学习第一现场，但随着 demo 增多，也开始出现一些重复问题：

- 每个 demo 都要重复处理模型初始化
- 环境变量和 provider 配置散落
- 只能在终端观察结果
- streaming、tool calling、parser、RAG 等逻辑难以统一复用
- 学习成果不容易转成可展示页面

因此创建 `AI-Journey-Land`，专门承接二次验证、工程化重构和可视化展示。

## 两个仓库的分工

### AI-Journey-Fighting

定位：学习第一实验地。

主要职责：

- 保留原始 demo
- 记录学习过程
- 记录踩坑与修复
- 产出 drafts
- 整理 VitePress 文档
- 维护 AI 概念地图

### AI-Journey-Land

定位：AI Demo 工程化展示平台。

主要职责：

- 把成熟 demo 包装成后端接口
- 提供统一模型调用能力
- 提供前端交互页面
- 支持 streaming、tool calling、structured output 等展示能力
- 作为个人 AI Demo Hub 长期演进

## 为什么要分开

分开是合理的。

如果继续把平台化代码放在 Fighting 里，仓库会同时承担太多职责：

- 学习草稿
- 原始 demo
- 修复 demo
- VitePress 文档站
- NestJS 后端
- 前端展示平台
- 部署配置

这会让项目边界变重，也会让学习记录和工程化代码互相干扰。

拆成两个仓库后：

- Fighting 可以保持真实、松散、可探索
- Land 可以保持工程化、结构化、可展示

这两个方向并不冲突，反而能形成一个很好的学习闭环。

## 当前阶段目标

当前阶段先不急着实现复杂功能。

更重要的是先确定：

- 平台定位
- 仓库边界
- monorepo 结构
- 第一批 demo
- API 形态
- 前端展示方式
- 部署策略

确认这些以后，再开始 scaffold 代码，会比直接开写更稳。

## 第一批适合迁移的 demo

建议优先选择低依赖、效果清晰、能体现工程化价值的 demo：

1. Prompt Template
   展示 prompt 变量、Few-shot、Example Selector。

2. Structured Output
   展示 schema 约束、parser、错误修复、稳定 JSON 输出。

3. Runnable
   展示 chain、branch、retry、fallback。

4. Tool Calling
   展示模型如何选择工具、生成参数、接收工具结果。

5. RAG / Memory
   展示检索增强、上下文拼接和历史记忆。

## 成功标准

第一阶段完成时，至少应该做到：

- 后端有一个统一 demo API
- 前端能列出 demo
- 可以选择一个 demo 运行
- 可以看到输入、输出、运行状态
- 至少一个 demo 支持 SSE 流式输出
- 每个 demo 能链接回 Fighting 中的源码或文档

做到这些，就说明平台的最小闭环已经成立。

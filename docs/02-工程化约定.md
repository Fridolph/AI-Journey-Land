# 工程化约定

## 1. Monorepo

当前仓库采用 `pnpm workspace + Turbo`。

目录分层：

- `apps/api`：NestJS 后端，负责真实 AI 调用、密钥保护、REST API 与 SSE。
- `apps/web`：Nuxt 4 + Vue 3 + Nuxt UI 前端，负责 demo 展示和交互。
- `packages/ai-core`：统一模型初始化与 AI 通用能力。
- `packages/demo-registry`：demo 元信息注册中心。
- `packages/shared`：共享 DTO、类型与 Zod schema。

根目录脚本：

```bash
pnpm dev
pnpm build
pnpm lint
pnpm format
pnpm format:check
pnpm typecheck
pnpm test
```

格式化与 lint 暂定使用 Oxc 工具链：

- `oxlint` 负责 lint。
- `oxfmt` 负责 format。

## 2. AI 调用

所有真实模型调用必须发生在 `apps/api` 或后端 package 中。

禁止：

- 前端读取 API Key。
- 前端直接调用模型 provider。
- 将 `.env` 提交到仓库。

配置示例参考 `apps/api/.env.example`，当前支持的变量：

```dotenv
# Provider 选择
AI_PROVIDER=openai       # openai | deepseek

# OpenAI-compatible（DashScope / Qwen）
OPENAI_API_KEY=sk-xx
OPENAI_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
MODEL_NAME=qwen-plus

# DeepSeek
DEEPSEEK_API_KEY=sk-xx
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL_NAME=deepseek-v4-flash
```

`packages/ai-core` 提供 `createChatModel()`，后续 provider adapter、embedding factory、stream helper 都优先沉淀到这里。

## 3. Demo Registry

每个 demo 至少要注册：

- `id`
- 中文名称
- 学习目标
- 分类与 tags
- 前端路由 `routePath`
- API namespace `apiNamespace`
- 展示模式 `displayMode`
- owner package `ownerPackage`
- 输入字段
- 是否支持 streaming
- 来源链接
- 已知限制

Land 不直接批量搬运 Fighting 的 examples。每个 demo 进入 Land 前都要明确输入、输出、运行方式、页面展示方式和来源上下文。

当前 `displayMode` 支持：

- `custom-page`：该 demo 有独立页面布局和交互逻辑。
- `generic-runner`：该 demo 可以复用通用输入/输出 runner。

Registry 是 Web 导航、API catalog 和文档展示的单一事实源。新增 demo 时优先更新 registry，再补对应 API module 与页面。

每完成一个 demo，都要在 `docs/demos/<demo-id>/` 下维护对应文档。目录名必须与 registry 中的 `demo.id` 保持一致，例如：

```text
docs/demos/
  prompt-template-weekly-report/
    总览.md
    前端复盘.md
    后端与AI复盘.md
```

每个 demo 至少要补三篇稳定文档：

- `总览.md`：概括 demo 目标、开发情况、难点要点和主要实现思路，不按前后端拆分。
- `前端复盘.md`：站在前端工程师视角，复盘页面分层、交互、AI 输出展示方式、安全、性能、样式和可优化方案。
- `后端与AI复盘.md`：站在后端和 AI 工程视角，复盘 API 逻辑交互、数据结构、模型调用封装、方案抉择、候选方案和后续综合服务扩展。

文档内容至少说明：

- 页面如何设计、如何分层。
- 关键交互如何处理。
- API 如何实现、数据如何流转。
- 使用了哪些 AI、前端、后端技术。
- 从前端、AI、后端三个视角分别有哪些可优化点，以及如何评估优化是否有效。

如果 demo 后续持续迭代，可以在同目录继续增加 `优化记录.md`、`评测记录.md`、`设计草稿.md` 等文档。基础三件套文件名尽量保持不变，便于后续维护和索引。

## 4. 服务边界约定

当前阶段采用“微服务思维、模块化单体落地”。

部署单元仍保持简单：

- `apps/web`：一个 Nuxt 前端应用。
- `apps/api`：一个 NestJS 后端应用。

但代码边界按 demo feature 拆分：

- Web 首页只做橱窗 catalog。
- Web 详情页使用 `/demos/:id`，复杂 demo 可以拥有自己的页面组件。
- API 保留公共 catalog 接口。
- 每个 demo 拥有独立 Nest module/service，并通过统一 runner 契约接入 `DemosService`。

第一阶段暂时不把每个 demo 拆成 `apps/demo-xxx-api` 或 `apps/demo-xxx-web`，原因是：

- 当前 demo 数量和复杂度还不足以支撑真实微服务成本。
- 先练清楚 registry、API namespace、输入输出 schema、SSE 事件和页面边界。
- 等某个 demo 演进成复杂 RAG、Agent、语音或长任务系统，再把该 demo module 提升为独立服务。

这能保留微服务的思维训练，又避免初始化阶段被部署、网关、鉴权、观测和跨服务调试拖慢。

## 5. API 与 SSE

当前 API 基线：

```http
GET /api/health
GET /api/demos
GET /api/demos/:id
POST /api/demos/:id/run
POST /api/demos/:id/stream
```

普通运行返回：

```json
{
  "demoId": "prompt-template-weekly-report",
  "status": "success",
  "output": "..."
}
```

流式运行使用 SSE：

```text
event: meta
data: {"demoId":"prompt-template-weekly-report","status":"started"}

event: token
data: {"text":"..."}

event: done
data: {"status":"success"}
```

失败时返回：

```text
event: error
data: {"status":"error","message":"..."}
```

## 6. Git 分支与协作规范

### 分支模型

```text
main          ← 主分支 / 发布（展示）分支
  └── dev     ← 开发分支，保持最新
       └── feat/#<issue>-<short-desc>   ← feature 分支，从 dev checkout
```

### 分支职责

- `main`：稳定的、可展示的版本。只接受来自 `dev` 的 squash merge，不直接 commit。
- `dev`：开发集成分支。所有 feature 分支合并到这里，保持最新代码。
- `feat/#<issue>-<short-desc>`：功能/修复分支，从 `dev` 切出，完成后提 PR 合并回 `dev`。

发布分支边界：

- issue 不从 `main` 切分支开发。
- issue 分支不直接合并到 `main`。
- `main` 只接受稳定发布合并，发布前必须确认 `dev` 已通过当前阶段要求的自测和人工验证。

### 日常开发流程

```bash
# 1. 切到 dev 并拉取最新
git checkout dev
git pull origin dev

# 2. 从 dev 切出 feature 分支（命名格式：feat/#<issue>-<short-desc>）
git checkout -b feat/#1-test-infrastructure

# 3. 开发、自测、提交
git add .
git commit -m "feat(#1): 搭建测试基础设施"

# 4. 推送到远端
git push origin feat/#1-test-infrastructure

# 5. 创建 PR 合并到 dev（通过 GitHub）
# 或者直接本地合并（小团队阶段）：
git checkout dev
git merge feat/#1-test-infrastructure
git push origin dev
```

### GitHub Issue 完整开发流程

每个 issue 必须从 `dev` 切出独立分支开发，并在完成后合并回 `dev`。`main` 只承担发布职责，不直接承接 issue 开发。

1. **先有 Issue，再开发**：每个开发任务必须先有 issue。issue 至少写清背景、目标、非目标、验收标准和测试计划。
2. **确认范围**：阅读 issue，明确本次目标、验收标准、影响模块和预计增删改文件。
3. **Plan / TDD**：进入实现前先拆实现计划和测试策略。API、数据库、跨端契约、AI prompt、SSE、鉴权、支付等容易回归的区域，必须先明确要覆盖的正常路径、边界路径和错误路径。
4. **同步基线**：执行 `git status`，确认工作区状态；切到 `dev` 并拉取远端最新代码。
5. **创建分支**：从 `dev` 切出 `feat/#<issue>-<short-desc>`、`fix/#<issue>-<short-desc>` 或 `docs/#<issue>-<short-desc>`。
6. **按框架实践开发**：API server 遵循 NestJS module/service/controller/provider 分层；Web 遵循 Nuxt 4、Vue 3、Nuxt UI 的页面、组件和 composable 分层。
7. **控制范围**：发现旁支问题时优先记录新 issue，不混进当前 issue；只有它阻塞当前验收时，才允许纳入本次开发，并在开发日志中说明原因。
8. **同步测试**：新增或修改功能时补充对应测试，测试放到领域模块的 `__tests__` 目录。
9. **Review 自查**：提交前检查是否符合 issue 目标，是否有无关改动，是否需要同步文档、API client、Swagger/OpenAPI、README、`.env.example` 或示例代码。
10. **先自测**：至少运行 `pnpm typecheck && pnpm test`；涉及格式、lint、构建或页面交互时同步运行 `pnpm format:check`、`pnpm lint`、`pnpm build` 或浏览器验证。
11. **写开发日志**：自测通过后，在 `docs/issues/` 下按 issue 号记录开发范围、关键实现、测试结果和遗留风险。
12. **提交推送**：按 Commit 格式提交，并 push issue 分支到远端。
13. **合并回 dev**：创建 PR 合并到 `dev`，或小团队阶段按约定本地合并后 push `dev`。
14. **关闭 issue**：合并完成后，在 issue 中补充开发信息、验证结果、PR/commit/文档链接，确认验收后关闭。

### Issue 内容模板

创建 issue 时至少包含：

```markdown
## 背景

为什么现在要做？

## 目标

- 本次要完成什么？

## 非目标

- 本次明确不做什么？

## 验收标准

- 如何判断完成？

## 测试计划

- 单元测试：
- 集成测试：
- 手动验证：
- 回归风险：
```

### Issue 开发日志

每个 issue 完成前都要补开发日志，目录固定为 `docs/issues/`。

文件命名：

```text
docs/issues/issue-006-api-common.md
docs/issues/issue-007-ai-core.md
```

日志至少包含：

- Issue 链接与标题
- 开发分支
- 开发范围与非目标
- 关键文件变更
- 实现说明与方案取舍
- 自测命令与结果
- 前端人工验证记录（涉及 UI 时必填）
- 数据库 / 环境变量 / 依赖 / Docker / CI 变更影响与回滚方式（涉及时必填）
- 遗留风险与后续优化
- 合并、关闭记录

### 特殊变更检查

涉及下列内容时，必须在 issue 和开发日志中写清影响范围、升级方式和回滚方式：

- 数据库 schema、migration、种子数据或索引。
- 环境变量、密钥命名、provider 配置或 `.env.example`。
- `package.json`、`pnpm-lock.yaml`、Node/pnpm 版本、Turbo 配置。
- Docker、CI、部署脚本或运行时启动命令。
- 对外 API 契约、SSE 事件、共享 DTO、SDK/API client 或 Swagger/OpenAPI。
- AI prompt、模型名称、provider adapter、结构化输出 schema 或评测逻辑。

涉及 UI 时，开发日志至少说明桌面端和移动端关键路径是否已人工验证；必要时附浏览器验证记录或截图路径。

### Definition of Done

一个 issue 只有同时满足以下条件，才视为完成：

- 实现满足 issue 验收标准，且未混入无关改动。
- 测试、类型检查和必要的 lint/format/build 已通过。
- 相关文档、demo 三件套、README、`.env.example`、API 契约或示例代码已同步。
- 安全风险已自查，不暴露密钥，不把后端专属配置泄露给前端。
- 特殊变更已写清升级影响和回滚方式。
- 开发日志、PR/commit、issue 之间可以互相追溯。

### 发布流程

当 `dev` 分支通过全部自测、准备好发布时：

```bash
git checkout main
git merge --squash dev
git commit -m "release: M1 工程基础夯实完成"
git push origin main

# 发布完成后切回 dev 继续开发
git checkout dev
```

### Commit 格式

```text
<type>(#<issue>): <简短描述>

类型：
  feat     - 新功能
  fix      - 修复
  refactor - 重构
  docs     - 文档
  test     - 测试
  chore    - 工程配置
  release  - 发布

示例：
  feat(#1): 搭建 vitest 测试基础设施
  refactor(#2): 重构 createChatModel 为工厂模式
  docs(#5): 补充测试规范文档
```

### 禁止操作

- 禁止直接向 `main` 提交
- 禁止 `push --force` 到 `main` 或 `dev`
- 禁止跳过 pre-commit hook
- 禁止提交 `.env` 或含密钥的文件

## 7. 代码组织与注释规范

### 通用原则

- 遵循 SOLID，以清晰职责和可维护边界优先。
- 单个文件尽量不超过 500 行；超过时优先按职责拆分为 service、factory、adapter、types、utils 或组件子模块。
- 不做过度拆函数、过度抽象和过早优化；同类逻辑出现 3 处以上重复，再提取公共能力。
- 优先使用常见 API 和可读写法，允许面向对象和函数式编程组合使用，但避免生僻、难以维护的技巧。
- 安全性优先于炫技：密钥、provider 配置、数据库连接和外部服务凭证都只能停留在后端环境变量或安全配置层。

### TypeScript 类型

- 单个文件类型定义超过 3 个时，拆到同目录 `.types.ts` 文件。
- 对外导出的 type、interface、class、enum 需要标准 TSDoc。
- 关键字段需要用 TSDoc 说明业务含义、单位、取值范围或安全注意事项。
- DTO、schema、registry meta 的类型优先沉淀到 `packages/shared` 或对应 feature 的 `.types.ts`，避免散落在 controller 或页面组件里。

### 方法与注释

- API controller 方法、service 对外方法、AI 调用封装方法都应添加标准 TSDoc。
- 核心业务逻辑可以使用 `//` 注释解释“为什么这样做”，不要写重复代码字面含义的注释。
- 注释要服务维护者理解边界、异常路径、第三方 API 限制或安全原因。

## 8. NestJS Module/Service/Controller 写法规约

### Module 组织

每个 demo 拥有独立 Nest module，通过 `DemosModule` 统一导入：

```typescript
// demos.module.ts
@Module({
  imports: [PromptTemplateWeeklyReportModule], // 新增 demo module 在此注册
  controllers: [DemosController],
  providers: [DemosService],
})
export class DemosModule {}
```

### Service 实现

每个 demo service 必须：

- 实现 `DemoRunner` 接口（`demoId`、`run()`、`stream()`）
- 通过 `DemosService` 的 `runners` Map 注册
- 使用 `@ai-journey-land/ai-core` 的 `createChatModel()` 工厂（不从 ConfigService 直接拼配置）
- 使用 `@ai-journey-land/shared` 的统一 schema 校验输入
- 不得在 service 中直接定义 provider 类型或 env 变量名

```typescript
@Injectable()
export class MyDemoService implements DemoRunner {
  readonly demoId = 'my-demo'

  constructor(private readonly configService: ConfigService) {}

  async run(body: unknown): Promise<string> {
    /* ... */
  }
  async *stream(body: unknown): AsyncGenerator<string> {
    /* ... */
  }
}
```

### Controller 约定

- 公共 catalog 接口放 `DemosController`（`GET /api/demos`、`GET /api/demos/:id`）
- 运行接口放 `DemosController`（`POST /api/demos/:id/run`、`POST /api/demos/:id/stream`）
- 复杂 demo 如需独立接口，可申请独立 controller，通过 `/api/<namespace>/...` 暴露
- SSE 响应统一使用 `prepareSseResponse()` 和 `writeSseEvent()` 工具

### 错误处理

- AI 配置缺失 → `AiConfigurationError`（`ai-core` 提供），controller 统一捕获转换 503
- 输入校验失败 → `BadRequestException`（NestJS 内置）
- Demo 不存在 → `NotFoundException`（NestJS 内置）

## 9. 测试与自测约定

### 测试目录

测试文件按 DDD/feature 边界放到对应模块的 `__tests__` 目录：

```text
apps/api/src/demos/prompt-template-weekly-report/__tests__/
packages/ai-core/src/__tests__/
packages/shared/src/__tests__/
```

命名建议：

- `*.spec.ts`：偏 module、controller、service 集成测试。
- `*.test.ts`：偏纯函数、schema、工具函数测试。

### 测试质量

- 测试必须验证真实行为、边界和错误路径，不写只为覆盖率存在的模板测试。
- 禁止为了让测试通过而硬编码实现或在测试脚本中写死与实现强绑定的对齐逻辑。
- AI 模型调用必须 mock，不依赖真实 API key 或外部网络。
- Bug 修复先补复现测试，再修代码。

### 自测命令

每个 issue 至少执行：

```bash
pnpm typecheck
pnpm test
```

按改动范围追加：

```bash
pnpm format:check
pnpm lint
pnpm build
```

前端交互改动还需要浏览器验证关键路径；AI/API 改动需要验证成功路径、配置缺失路径和错误返回。

## 10. Demo 接入 Checklist

新增 demo 的完整步骤：

1. **注册元信息**：在 `packages/demo-registry/src/demos/<demo-id>.ts` 创建 `DemoMeta`
2. **注册导出**：在 `packages/demo-registry/src/index.ts` 的 `demos` 数组中添加
3. **定义输入**：在 registry 中声明 `inputFields`，必要时在 `shared` 中添加 demo 特定的 input schema
4. **创建后端模块**：在 `apps/api/src/demos/<demo-id>/` 创建 module + service
5. **注册 runner**：在 `DemosService` 构造函数中注入新 service 并加入 `runners` Map
6. **导入模块**：在 `DemosModule` 的 `imports` 中添加新 module
7. **创建前端页面**（`displayMode: 'custom-page'`）：在 `apps/web/app/pages/demos/` 添加路由
8. **或复用通用 runner**（`displayMode: 'generic-runner'`）：无需额外页面
9. **补文档**：在 `docs/demos/<demo-id>/` 下创建 `总览.md`、`前端复盘.md`、`后端与AI复盘.md`
10. **补测试**：后端 service + API 测试，覆盖率不低于 60%
11. **自测验证**：`pnpm typecheck && pnpm test` 全部通过
12. **提交 PR**：按 Git 分支规范提交到 `dev`

## 9. UI 组件约定

- **最小字号 14px**（`text-sm`），不使用 `text-xs`（12px）作为正文
- **组件尺寸默认**：不传 `size="xs"` / `size="sm"`，使用 Nuxt UI 默认尺寸
- 表单标题用 `text-[#334155] text-[0.82rem] font-bold`
- 颜色优先使用 Nuxt UI 语义 token：`text-muted` / `text-highlighted` / `text-primary` / `bg-muted` / `bg-primary`
